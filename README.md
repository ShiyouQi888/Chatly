# Chatly

> 连接更有趣的人 —— 移动端聊天通讯 App

基于《移动端聊天通讯软件功能书》（47 节 PRD）实现。覆盖 **聊天 / 动态 / 发现 / 我** 四大板块，  
其中**聊天 / 动态 / 发现 / 位置 / 群投票已接通独立后端**（REST + WebSocket + SQLite + JWT），
通知 / 在线状态等仍为原型数据。

> 每一页都遵守同一条底线：**界面上的每个数字、每句话、每次点击都要能追到库里的一行数据**。  
> 追不到的，就标「未接入」并禁用 —— 不做一个点了弹 toast 假装成功的假按钮。

## 运行

需要 **两个进程**（前端 5198、后端 3002）。先装依赖并灌入演示数据：

```bash
# 1) 后端
cd server
npm install
npm run seed     # 首次：写入 6 个演示用户 + 会话 + 消息（幂等）

npm run dev      # http://127.0.0.1:3002  （node --watch，改代码自动重载）

# 2) 前端（另开一个终端，回到项目根目录）
npm install
npm run dev      # http://127.0.0.1:5198
```

## 后端

独立进程，**零外部数据库依赖**（用 Node 内置 `node:sqlite`，需 Node ≥ 22.5）。

| 能力 | 实现                                                                                                                 |
| -- | ------------------------------------------------------------------------------------------------------------------ |
| 认证 | JWT（7 天），REST 用 `Authorization: Bearer`，WebSocket 用 `?token=`                                                      |
| 密码 | `node:crypto` scrypt（`scrypt$salt$hash`），不引 bcrypt                                                                 |
| 实时 | `ws` —— `hello` / `message.new` / `message.revoked` / `conversation.read` / `typing` / `presence` / `user.updated` / `conversation.updated` / `poll.updated` |
| 存储 | SQLite（WAL），13 张表：`users` / `conversations` / `conversation_members` / `messages` / `moments` / `moment_media` / `moment_likes` / `moment_comments` / `follows` / `polls` / `poll_options` / `poll_votes` / `poll_replies` |
| 资料 | 扩展字段 `gender` / `birthday` / `region` / `tags`，用幂等 `ALTER TABLE` 迁移（SQLite 没有 `ADD COLUMN IF NOT EXISTS`）          |
| 上传 | multer → `server/uploads/`；附件 20MB、头像 5MB；扩展名与 MIME 双重校验                                                           |

发消息走 REST（便于落库并拿到消息 id），WebSocket 只负责下行推送与 `typing` 上行。

> `users` 表结构变更一律走 `db.js` 里的 `addColumnIfMissing()`，不要让人去跑 `npm run reset` ——  
> reset 会连会话和消息一起清掉。`seed.js` 的 `backfillProfiles()` 只补空字段，老库直接启动即可。

```bash
cd server
npm run dev      # node --watch src/index.js
npm run reset    # 清空并重建演示数据
node test/e2e.mjs   # 后端端到端测试（70 项断言）
```

## 布局形态

**纯 H5 竖屏固定布局**，不含手机外壳（无刘海 / 无状态栏 / 无 Home Indicator）。

- 桌面预览：内容区固定 **390px 宽**，垂直居中，最大高度 `min(100dvh, 900px)`，两侧留中性浅底。
- 真机 / 窄屏（≤ 440px）：内容区**铺满整个视口**（`100dvh`），去掉圆角与阴影。
- 顶部留白由 `--safe-top` 统一控制（真机上由系统状态栏占位，桌面预览需显式留出）。
- 底部导航用 `env(safe-area-inset-bottom)` 适配全面屏手势区。

在浏览器 DevTools 里切到 iPhone / Android 设备模式即可看到真实效果，无需额外配置。

<details>

<summary><b>动态 —— 已接通后端</b>（PRD §16）</summary>

内容流只有一个入口：底部「动态」Tab。三个筛选各有各的语义，别混：

| 筛选 | 拿到什么 | 排序 |
| --- | --- | --- |
| 朋友 | 我**看得见**的全部 —— 公开的 + 互关好友「仅好友」的 + 我自己的（含仅自己可见） | 时间倒序 |
| 我的 | 只有我自己发的 | 时间倒序 |
| 热门 | 同上「看得见的」，按热度（赞 + 评论加权） | 热度倒序 |

**真实可用：**

- **展示**：图片九宫格（1 张随比例、3 张及以上三列方图）、真实加载的缩略图（`naturalWidth > 0`）、  
  **视频播放器（横竖屏自适应，见下）**、音乐卡片（**播放未接入，按钮禁用并写明**，不做「换个图标就当播了」的假播放）、  
  话题、定位、可见范围徽标（只标「仅好友 / 仅自己」，公开的不占地方）、相对时间（刚刚 / N 分钟前 / 昨天 HH:mm / M/D）。
- **发布 / 编辑**：整屏面板 —— 文案（2000 字，按**码点**算，emoji 不虚高）、最多 9 张图 **或 1 个视频**、  
  话题、定位、可见范围三选一（公开 / 仅好友 / 仅自己，各带一句说明）。编辑时同步预填，不会先闪一帧空表单。
  **媒体选中即上传**（不是「先本地预览、发布时才传」）：图 / 视频就是这条动态的内容，  
  发布失败却留一堆孤儿文件是最难收拾的状态；代价是取消要清，由清理脚本按「无人引用」回收。
- **视频动态**（一条动态要么图文、要么 1 个视频，**两者互斥** —— 朋友圈也是这个规则；  
  九宫格里塞小视频要同时起好几个解码器，滚动起来手机发烫而收益几乎为零）：
  - 上限：**1 个**（`MAX_VIDEO`）、**80 MB**、**3 分钟**。图片走另一个接口（12 MB），  
    上传接口按 `?kind=` 分流 —— multer 的 `limits` 只能给一个值，得在**解析之前**决定挂哪个中间件。
  - 发布前先读元数据（临时 `<video>` 读 `videoWidth/videoHeight/duration`）：时长超限不用白传 80 MB，  
    宽高一起落库（`moment_media.width/height/duration`）→ 列表**在加载视频之前**就按真实比例占位，不会先按方的渲染再跳。
  - 读不出元数据就存 NULL，**不编数字**（编个 0 会让 `aspect-ratio` 直接失效）。
  - 媒体三道校验：地址白名单 → 文件真实存在（动态是「刚发布」，与消息「历史记录」的取舍不同）  
    → 视频还要验**文件头魔数**（扩展名与 MIME 都是客户端给的，改名成 `.mp4` 的文本两道都能过）。
  - **自建播放器**（`VideoPlayer.jsx`，不用原生 `controls`）：原生控件会带出「画中画 / 下载」这些我们**没接**的按钮  
    （点了没反应 = 坏功能），且不管容器比例、各浏览器长得不一样。自己的控制条：播放/暂停、进度拖拽、时间、静音、全屏，
    主操作（播放 / 暂停）是品牌色实心圆，进度填充也走品牌渐变；控制条播放中 5 秒自动收起，点画面 / 移指针立刻回来；  
    点画面时中央有一次播放/暂停的闪动反馈。**画面上不叠任何文字**（文件名放在下方 `.mv-meta`）。
  - **横竖屏自适应**：`onLoadedMetadata` 拿到真实宽高 → 夹取比例（横 1~1.91 / 竖 0.6~1）写进 CSS 变量 `--ar`，  
    打 `is-landscape` / `is-portrait` 类。两种方向**约束不同**：横屏铺满宽度；竖屏高度优先且封顶 380px  
    （否则一条 9:16 能把卡片顶成两屏高）。画面一律 `object-fit: contain` —— 裁掉半张脸比多两条黑边难看得多。  
    ⚠️ 只封 `max-height` 不够：容器还是满宽，画面会在两侧留黑边。所以要按 `max-height × --ar` **收宽度**，容器才正好是画面形状。
  - ⚠️ **全屏查看器里反过来**：外层 `.mv-vp` 只负责居中，尺寸完全交给播放器自己（`aspect-ratio` + `max-height: 100%`）。
    **容器必须正好是画面的形状** —— 一旦撑满整个舞台，画面居中留大片纯黑、控制条被推到屏幕最下沿，
    控件明明全是自己写的，整体却和浏览器自带播放器一模一样（详见「媒体查看器」一节）。
  - 列表里的视频是「封面 + 播放按钮 + 时长角标」，点了进全屏查看器（不是原地播）；查看器里静音自动起播。
- **管理**：自己的动态才有「编辑 / 删除」（卡片右上角 ⋯）；删除有二次确认。  
  别人的动态只能点赞、评论。**服务端才是真正的拦截**，前端只是不显示入口。
- **点赞**：乐观更新（点了立刻变红）+ 失败回滚，最终以服务端返回的 `liked / likeCount` 为准。
- **评论**：整屏详情页 —— 评论树（回复挂在父评论下缩进显示，带「回复 X：」前缀）、  
  删评论（自己发的或自己动态下的都能删）、点赞的人（头像簇）。
- **可见范围**：`public` 谁都能看、`friends` 只有**互相关注**能看、`private` 只有作者。  
  列表与详情共用同一份判定（`visibleTo()`），不会出现「列表看不见、点进去却能看」。  
  看不见的人拿到的详情是 **404 而不是 403** —— 与「不存在」同码，不泄漏「这条其实存在」。
- **关注关系**：资料页可关注 / 取关；互关是「仅好友」可见的前提。
- **搜索**：结果里的「动态」也是真数据，点开直接进详情页。

投票、活动、链接卡片、分享到外部、举报。

## 群聊

群聊的管理入口有两条，都通到同一个整屏层「群设置」：

- 聊天页**点顶部群头像 / 群名**
- 聊天页「⋯」→ 会话设置 → 「群设置」

会话设置（「⋯」）里仍然只有**个人偏好**（置顶 / 免打扰 / 删会话），群资料一律在群设置里改 ——
两处都能改群名的话，同一份状态就有两个写入点。

### 权限

|            | 群主 owner | 管理员 admin | 成员 member |
| ---------- | --------- | ---------- | --------- |
| 改群名 / 群头像 / 发公告 | ✅ | ✅ | — |
| 全员禁言 / 仅管理员发言  | ✅ | ✅ | — |
| 发起投票 / 投票           | ✅ | ✅ | ✅（受禁言开关约束） |
| 提前结束**自己发起的**投票 | ✅ | ✅ | ✅ |
| 邀请成员                | ✅ | ✅ | ✅ |
| 移出**普通成员**        | ✅ | ✅ | — |
| 移出**管理员** / 设 · 撤管理员 | ✅ | — | — |
| 退出群聊                | —（需先转让群，未接入） | ✅ | ✅ |

规则在服务端 `chat.js` 的 `canManage` / `isOwner` / `removeMember` / `setMemberRole`，
前端只是**不显示**没权限的入口；真正的拦截始终在服务端（自检里两边都钉了）。

### 不显然的几个点

- **群公告要出现在聊天页顶部**，不能只躺在设置页里 —— 那等于没有。
  所以 `.room-ann` 是顶栏与消息区之间的常驻条：默认压成两行，点一下展开全文。
  也不做成开屏弹窗：一进来就占掉半屏，看消息的人会烦。
- **群头像不能借用成员的头像。** 会话列表原来对群聊也走「没头像就用第一个非我成员的」，
  结果那个人一换头像群头像就跟着变，看着还像「群是某个人开的」。
  现在群没设头像时服务端返回 `null`，前端用群名生成稳定的渐变底图。
- **改群资料要推给所有成员**（`broadcastToUsers(memberIds(cid), 'conversation.updated', …)`）：
  别人开着这个群，群名一改他的标题栏还是旧的，那不叫实时。
  移人时**要把被移出的人也算进广播名单**，否则他列表里还挂着这个群，点进去才发现「已经不在群里了」。
- **`PATCH /conversations/:id` 一个接口管两类字段**：个人偏好（`pinned` / `muted`，写在自己的成员行上）
  与群资料（`title` / `avatar` / `announcement` / `muteAll` / `adminOnly`，需要 `canManage`）。
  分成两个接口的话，「改个群名」和「开个免打扰」要走两条完全不同的路。
  服务端 `updateGroup()` **只改传进来的字段**，局部更新不会把别的字段冲成 `null`。
- **群头像和用户头像同一套校验**：只允许 `preset:<n>` 或自家 `/uploads/` 下的文件，
  且文件必须真的存在。不校验的话客户端能把任意 URL 写成群头像，别人一进群就去请求那个地址。
  传空串 = 清空，回到名字生成的底图。
- **群主的「退出群聊」是禁用并说明原因的**，不是点了才报 403 —— 群里不能没有群主，
  而管理员的权限又是从群主那里来的，群主一没整套权限模型就悬空了。转让群本次未做，界面上也不给入口。

## 动态

动态（PRD §16「轻量内容流」）的数据全部来自后端，五个表：
`moments` / `moment_media` / `moment_likes` / `moment_comments` / `follows`。

```
GET    /api/v1/moments?scope=friends|mine|hot&beforeId=&limit=
POST   /api/v1/moments                      发布
GET    /api/v1/moments/:id                  详情
PATCH  /api/v1/moments/:id                  编辑（仅作者）
DELETE /api/v1/moments/:id                  删除（仅作者）
POST   /api/v1/moments/:id/like             点赞 / 取消（同一接口来回切）
GET    /api/v1/moments/:id/likes            点赞的人
GET    /api/v1/moments/:id/comments         评论列表（扁平，靠 parentId 组树）
POST   /api/v1/moments/:id/comments         发评论 / 回复（带 parentId）
DELETE /api/v1/moments/:id/comments/:commentId
POST   /api/v1/moments/upload?kind=image|video    媒体上传（kind 在 query 上，见下）
POST   /api/v1/users/:id/follow  ·  DELETE 同路径   关注 / 取关
```

**`kind` 为什么放 query 而不是 multipart 字段**：multer 的 `limits` 一次只能给一个值
（图片 12 MB / 视频 80 MB），而挂哪个中间件必须**在解析 body 之前**决定 ——
multipart 的字段要等 multer 解析完才拿得到，那时中间件早就选好了。

### 可见范围是真的在拦

| 取值 | 谁能看 |
| --- | --- |
| `public` | 所有人 |
| `friends` | 作者 + **与作者互相关注**的人 |
| `private` | 只有作者 |

判定只有一处：`moment.js` 的 `visibleTo()`，列表与详情共用 —— 分成两份一定会走岔，
典型症状是「列表里看不见、点进去却能看」。自检用**三个身份**交叉验证：
作者自己、互关好友（应该看得到）、单向关注的人（应该被挡住）。只测「好友看得到」是不够的，
把判定写成 `visibility !== 'private'` 也能过。

详情对看不见的人返回 **404 而不是 403** —— 与「不存在」同码，不泄漏「这条其实存在，只是你看不到」。

### 不显然的几个点

- **图片 / 视频选中即上传**，不是「先本地预览、发布时才传」。媒体就是这条动态的内容，
  发布失败却留下一堆孤儿文件是最难收拾的状态；代价是取消要清掉已传的文件，这个代价小得多。
  孤儿回收由 `scripts/lib/debris.mjs` 的 `purgeOrphanUploads()` 按「无人引用」负责，
  它的引用方要扫**四处**：`users.avatar`、`messages.file_url`、`conversations.avatar`、`moment_media.url`
  —— 少扫最后一处，第一次清理就把演示动态的照片全挪走了。
- **编辑是「媒体整体替换」**：传 `media` 就整套换掉，不传就不动；`kind` 跟着重算
  （有视频 → `video`，有图 → `image`，只有音乐 → `music`，都没有 → `text`）。
- **文本长度按码点算**（`[...s].length`）：`'😂'.length === 2`，不按码点算的话
  一条 emoji 满屏的动态会被前端判超长而服务端放过。
- **删除评论要校验「这条评论属于这条动态」**：只按 commentId 查的话，
  在 A 的详情页里传一个 B 的评论 id 就能删掉 B 的评论。
- **点赞是乐观更新 + 失败回滚**，但最终以服务端返回的 `liked / likeCount` 为准 ——
  本地 +1 只是让手快点下去立刻有反馈，别人的赞可能同时进来。
- **进入动态 Tab 会重新拉一次列表。** 动态没有 WebSocket 推送（不像聊天），
  只靠登录时那一次请求的话：停在列表上不动，别人新发的动态永远看不到。这也是朋友圈的行为。
- **`GET /moments/:id` 的 404 有歧义**（不存在 / 没权限），前端不为它做特殊文案，
  只说「动态不存在或你没有权限查看」。
- **视频与图片互斥要在服务端也挡一次**。前端在「选文件」那一步已经挡了，但列表渲染是
  「有视频就走播放器、否则走网格」的分支结构 —— 绕过界面直接 POST 混着发，
  会有一半媒体永远显示不出来。`assertMedia()` 里补一条，别只信前端。
- **视频要验文件头魔数**（`looksLikeVideo()`）。扩展名和 MIME 都是客户端给的，
  把一段文本改名成 `.mp4`、MIME 写 `video/mp4`，两道校验都能过 —— 传上来就是一个永远播不了的「视频动态」。
  读前 12 字节认容器：ISOBMFF `ftyp` / EBML / `RIFF....AVI ` / `OggS`。不合法就 `removeUpload()` 删掉刚落盘的文件再 400。
- **宽高只认正整数**，给 0 会让前端的 `aspect-ratio` 变成非法值，整块塌成一条线。
  客户端读不出来就存 NULL（前端退默认 16:9），**服务端不要编一个数**。
- **演示视频提前生成好放在仓库里**（`server/assets/seed/*.mp4`，ffmpeg 造的渐变动画，
  横屏 640×360 / 竖屏 360×640）。不在 seed 里现造 —— 那要求跑 `npm run reset` 的机器上装了编码器。
  seed 只负责复制进 `uploads/`；文件不在就跳过视频动态，其余种子照常写。

## 发现

```
GET    /api/v1/discover/recommend?tag=&limit=&offset=   推荐用户（带理由 / 排序）
GET    /api/v1/discover/nearby?limit=                   附近的人（按资料地区，无公里数）
GET    /api/v1/discover/tags                            兴趣标签聚合（人数 + 我是否填了）
GET    /api/v1/discover/groups                          可加入的**公开**兴趣群
POST   /api/v1/discover/groups/:id/join                 加入公开群（语义是「自己加自己」）
GET    /api/v1/users/:id/follow · DELETE 同路径         关注 / 取关（发现页复用动态那套）
```

### 三条硬规矩

写在 `server/src/discover.js` 头部，改这一页之前先看一遍：

1. **推荐理由必须可解释。** 只能由「共同群聊 / 共同兴趣标签 / 同城」算出来，
   算不出就给 `null`、前端不显示。不要写「可能认识」这种无法证伪的话 ——
   一句无法证伪的推荐语，等于没有推荐。
2. **距离不编公里数。** 库里没有经纬度。附近的人按资料里的**地区**匹配：
   同城 = 2 / 同省 = 1 / 其它 = 0，界面显示「同城 / 同省 / 地区名」并写明未开启定位。
   PRD 也要求「默认关闭精准位置展示」，正好一致。
3. **没有数据源的板块不做。** 活动、热门话题榜、精准定位附近都没有对应的表 ——
   前端渲染成禁用项并写明原因，不塞一批写死的活动卡片。

### 不显然的几个点

- **`conversations.discoverable`（幂等 `ADD COLUMN`，默认 0）**。不加这一列，
  发现页只能列出**所有**群 —— 等于把「设计部」这种工作群挂牌公开，任何人点一下就能进。
  种子里只对独立新建的兴趣群显式置 1。
- **加群语义是「自己加自己」**（不是邀请，所以不需要管理权限），
  但**必须校验 `discoverable`**，否则这就是一个「知道 id 就能进任意私人群」的越权口子（403）。
  已在内返回 `{ joined: false }`；加入后用 `broadcastToUsers([...prev, viewerId], 'conversation.updated', …)`
  广播 —— 少算了本人，他的会话列表不会立刻出现这个群。
- **排序权重是 `[following ? 0 : 1, groups, tags, near]`，第一位是「没关注」。**
  第一版漏了它，两个共同群聊的已关注熟人一直顶在最前，推荐等于把熟人重列一遍。
- **标签筛选在服务端做**（`u.tags LIKE '%"电影"%'`，**带引号**匹配，
  避免「电影」误命中「电影院」）。放前端过滤会因分页而漏人。
- **兴趣标签是从所有用户填过的标签聚合出来的**，不是写死那十个 ——
  用户填了「攀岩」就该能找到同类。我自己的标签排最前并标 `mine`。
- **关注接口的返回字段踩过一次坑**：`followCounts()` 早期返回 `{ following, followers }`，
  而路由写的是 `{ ...followCounts(id), following: isFollowing(...) }` ——
  对象展开把布尔值**覆盖成了数字**，客户端 `!!out.following` 恒为 true，
  于是「取关之后按钮还写着已关注」（库里其实已经删了）。
  现在计数改名为 `followingCount / followerCount`，且布尔一律写在展开**之后**；
  前端 `DiscoverStore` 额外只认 `typeof === 'boolean'`，类型不对就不采信。

## 群投票

PRD §14「群内可以快速发起投票」，四种能力全都落地：**单选 / 多选 / 匿名 / 截止时间**，
另加了一个 PRD 没写但缺了就很难受的**「发起人提前结束」**——没有它，一条把截止时间设成
30 天后的投票就只能挂在那里等。

两个入口，都通到同一份数据：

| 入口 | 位置 | 做什么 |
| --- | --- | --- |
| 发起 | 聊天页「+」→ 投票（**只在群聊出现**；私聊里这一项整个不存在，见下） | 填题目 / 2~10 个选项 / 多选 / 匿名 / 截止时间 |
| 查看全部 | 群设置 → 群投票 | 该群历史投票列表，点一条**跳到聊天里那条消息**并高亮 |

### 投票就是一条消息

投票在库里是 `messages.kind = 'poll'` + `poll_id` 指向 `polls` 行。
这么做而不是另起一套「群投票列表」：投票要出现在聊天记录里、要有已读回执、
要能被撤回、要能被引用回复 —— 这些消息层已经全都做好了，另起一套就得各做一遍。

四张表，而不是「一条消息里塞一段 JSON」：

```
polls          题目 / 单选多选 / 匿名 / 截止时间 / 谁发起 / 何时手动结束
poll_options   选项（带 sort，顺序就是创建时的顺序）
poll_votes     一行 = 某人对某个选项的一票（多选 = 同一人多行）
poll_replies   「谁投过票」的名册（一个人一条，靠唯一索引去重）
```

**票数不存字段，一律 `COUNT` 出来。** 在 `poll_options` 上放一个 `count` 列看着省事，
但投票 / 改票 / 取消投票三处都要记得加减一，漏一处就是一个永远对不上、而界面上看不出来的数字。

### 权限与可见性

| 操作 | 谁能做 |
| --- | --- |
| 发起 | **只有群聊有入口**（单聊面板里不存在这一项，服务端也拒：`投票只能在群聊里发起`）；群内任何成员，但受「全员禁言 / 仅管理员发言」约束 —— 投票表现为一条消息，禁言却能发起等于绕过群治理 |
| 投票 / 改票 / 取消 | 群里任何成员，且投票未结束 |
| 提前结束 | **只有发起人**（服务端 403，前端只是不显示入口） |
| 看列表 / 看详情 | 群成员；**群外人拿 404 而不是 403**（和动态详情同一个取舍：不泄漏「这条投票存在」） |

### 不显然的几个点

- ★★ **单聊里不是「禁用投票」，而是没有这一项。** 第一版把入口画成
  「投票 · 仅群聊」摆在那里 —— 那是错的口径：投票在两个人之间没有语义，
  界面上不该出现一个用户永远用不到的东西。判据也不同：自检断言的是
  **这一格不存在**（`plus-投票` 查不到），不是「它是 disabled」。
  ⚠️ 同时要断言**单聊面板的其它项还在**（图片/视频/位置/文件）——
  否则「整个面板没渲染」也会让「找不到投票」通过，那是假绿。
  群里若被「全员禁言 / 仅管理员发言」挡住，才回到 `disabled` + 写明原因 ——
  那种情况下功能是**存在**的，只是当前这个人暂时不能用，两件事不能混。
  服务端本来就挡着（私聊发起返回 400「投票只能在群聊里发起」），入口移除只是不让人白点。
- ★ **匿名是在服务端就不返回。** 非匿名时出参带 `voters`（投了哪些人，只到「人」不到「选了哪项」）；
  匿名时**整个 `voters` 字段都不出现**，不是空数组。前端渲染头像簇的判据是
  `Array.isArray(voters)` 而不是 `!anonymous` —— 后者一旦有人改了服务端出参，
  界面会安静地画出一片空白（少画），而不是把名字暴露出去（多画）。
  自检钉的是「出参里没有这个 key」，因为「界面上看不到名字」用「前端忘了隐藏」也能过。
- ★ **多选要「确认」才提交，单选点一下就投。** 多选如果在点第一下就提交，
  用户还没来得及选第二项，别人那边已经看到一票了。所以多选在气泡里攒成本地选中态，
  底部「确认投票」一次性把**完整选择**提交上去。
- ★ **提交的是「投票后的完整状态」，不是「增量」。** 同一个接口管三件事：
  传 1 个 = 换选项、传 N 个 = 整体覆盖、传**空数组 = 取消投票**。
  没有「取消」这条路的话，用户改错了就只能一直错着。
  服务端 `votePoll()` 是「先删掉我的所有票，再按传入的写一遍」——幂等，重复提交 `changed=false`。
- ⚠️ **取消投票必须同时清掉名册那一行**，否则界面上会出现「0 人投票，但头像簇里有我」。
- ⚠️ **撤回投票消息不删投票行。** 撤回的语义是「这条消息不作数了」，不是「投票的历史被抹掉」；
  投票行留着不影响任何统计（群设置列表只列**消息还在**的那些）。
- ⚠️ **过期 ≠ 手动结束。** `closed` 是「手动结束 **或** 过了截止时间」两者合成的判定（`isClosed()`），
  但 `closed_at` 只在**手动结束时**才写 —— 补上的话就分不清两种结束，
  「谁什么时候关的」这个信息就丢了。
- ⚠️ **题目在 `messages.content` 里存了一份副本**，这是全项目唯一一处刻意的冗余。
  `polls.question` 才是真源，`content` 只给会话列表的预览用（`[投票] 周六去哪？`），
  不这么做的话会话列表每一行都要 `LEFT JOIN polls`，而那是整个 App 最热的查询。
  它不会漂移，因为**投票发布后题目不可编辑**（没有 PATCH 接口）。
- ⚠️ **投票消息的详情不在消息出参里。** 消息只带 `pollId`，前端拿 id 集合走
  `GET /polls?ids=` 批量换 —— 把选项 / 票数 / 投票人塞进 `listMessages` 的话，
  「拉 50 条历史」就等于「拉 50 份投票明细」，而其中绝大多数根本不需要。
- ⚠️ **`ensureMessageKinds()` 会给老库整表重建**（SQLite 改不了 CHECK 约束），
  所以新装机器的路径**永远不会被执行** —— 迁移只能靠现造一个老库来验，
  见 `check-poll.mjs` 的 A 段。这一条对任何「加消息类型」的改动都成立。

### 接口

```
GET    /api/v1/polls?ids=1,2,3            批量取详情（聊天记录里按 pollId 换）
GET    /api/v1/polls/of/:conversationId   某群的投票列表（带 messageId，用于跳转）
POST   /api/v1/polls                      发起（同时建一条 kind='poll' 的消息）
POST   /api/v1/polls/:id/vote             投票 / 改票 / 取消（optionIds = 完整状态）
POST   /api/v1/polls/:id/close            发起人提前结束
WS     poll.updated                       有人投票 / 结束，推送**整份投票**
```

## 消息收藏

PRD §9「长按消息 → 收藏」与「消息多选批量 → 收藏」。三个入口：

| 入口 | 位置 | 做什么 |
| --- | --- | --- |
| 收藏 / 取消收藏 | **长按一条消息** → 菜单 | 单项开关，已收藏时菜单显示「取消收藏」 |
| 批量收藏 | 长按 → 菜单 →「多选」→ 底部工具栏「收藏」 | PRD §9 的「消息多选批量」 |
| 我的收藏 | 我页统计条 / 四宫格「收藏」 | 列表 + 「在聊天中查看」跳转 + 移除 |

> **加号面板里没有「收藏」。** 加号是「发一条新消息」的地方，而收藏的作用对象是
> **已有的一条消息** —— 放在那里语义上说不通（第一版画了个「收藏 · 未接入」的灰按钮，
> 收藏做完之后它仍然不该在那儿，所以直接拿掉）。

### 收藏是**快照**，不是引用

这是这一块最要紧的设计。收藏下来的内容**不跟着原消息走**：

- 对方**撤回**消息 → 收藏里的正文与文件地址**仍然完整**
- 消息被清理 / 会话被删 → 收藏还在，只是「在聊天中查看」跳不过去了（界面如实说明）

做成「指向 messages 的一行引用」的话，对方一撤回你的收藏就变成一条空记录 —— 那不叫收藏。

```
favorites   user_id / message_id / conversation_id / sender_id
            kind / content / file_url / file_name / file_size      ← 快照
            geo_* / poll_id                                          ← 快照
```

由此带来**一个必须一起处理的副作用**：快照的 `file_url` 是那个文件**最后的引用者**
（原消息已经删了），所以 `scripts/lib/debris.mjs` 的 `purgeOrphanUploads()`
必须把它算作引用方 —— 漏掉不是「少清理一个文件」，而是**把还在用的文件当孤儿挪走**，
界面上就是收藏里的图集体变破图。引用方清单现在有**五处**，加新功能时要一起来补。
`check-favorite.mjs` 的 B 段专门验这个（并且带反例：取消收藏后同一个文件**确实**被回收）。

### 不显然的几个点

- ★ **`message_id` 用 `ON DELETE SET NULL`，不是 CASCADE。** 消息被物理删掉时收藏要**活着**，
  只把跳转能力摘掉。产品侧没有「删除消息」（只有撤回），物理删除只发生在自检清理与会话级联。
- ★ **发送者的昵称与头像不抄快照，只存 `sender_id`，渲染时现查。**
  抄了就是「好友改名之后，收藏里还写着旧名字」。发送者注销（SET NULL）则退化成「已注销用户」。
- ★ **「已经收藏过」必须排在「已撤回」前面判断。** 一条消息先被收藏、之后被撤回时，
  用户再点「收藏」期望的是「它已经在收藏里了」，而不是一句「已撤回，不能收藏」——
  后者会让人以为收藏丢了。
- ⚠️ **批量收藏里混着一条已撤回的，只跳过它、其余照收**，并把 `skipped` 一起返回。
  整批失败会让用户「选了 10 条一条都没收藏上」，那只会让人觉得功能坏了。
  界面上也如实报数：「收藏 8 条，跳过 2 条（已撤回）」，不能只说「已收藏」。
- ⚠️ **收藏是私人的**：每条 SQL 都带 `user_id = ?`，别人的收藏 id 猜到了也读不到、删不掉。
  而「收藏**别人会话**里的消息」单独挡一次 403 —— 消息 id 是自增的，很好猜。
- ⚠️ **消息出参里的 `favorited` 必须一次 `IN` 查询算完**，别在循环里逐条查
  （一页 40 条消息就是 40 次查询）。
- ⚠️ **前端判断「收藏了没」用的是 FavoriteStore 里那个 Set，不是从收藏列表反推。**
  一条两年前的旧消息**不在收藏列表的第一页**，从列表里反查会得到「没收藏」——
  长按菜单就会错误地显示「收藏」（其实是「取消收藏」）。
  Set 由「拉历史时服务端给的 `favorited`」+「收藏时就地增删」共同维护。
- ⚠️ **多选的「已选」状态绑在会话上**：切会话时要一起清掉，
  否则底部「已选 3 条」指的是上一个房间里的消息。
- ⚠️ **`purgeOrphanUploads()` 的扫描顺序**：必须先清消息与收藏、再回收文件；
  反过来刚发的图还被指着，扫不到（这条老规矩对收藏同样成立）。

### 接口

```
GET    /api/v1/favorites                  我的收藏（beforeId 游标 + limit + total）
POST   /api/v1/favorites                  收藏一条（幂等：重复收藏 → created:false）
POST   /api/v1/favorites/batch            批量收藏（返回 added / skipped，逐条判定）
DELETE /api/v1/favorites?messageId=N      按消息取消（气泡开关走这条）
DELETE /api/v1/favorites/:id              按收藏 id 取消（收藏列表里移除）
POST   /api/v1/favorites/unbatch          批量取消
```

## 媒体查看器

点开一条**图片**或**视频**消息，会全屏打开查看器：

|      | 行为                                    |
| ---- | ------------------------------------- |
| 关闭   | 左上角「关闭」按钮 / 点空白处 / `Esc`               |
| 保存   | 右上角「保存」按钮（真实下载到本地，视频同样）              |
| 图片   | 等比缩放居中显示                              |
| 视频   | 自己的播放器（`VideoPlayer`，`mode="full"`）—— 静音起播，控制条贴在画面下沿 |
| 底部   | 文件名 · 体积 · 视频时长                        |

发送入口在输入框的「+」里：**图片 / 视频 / 文件 / 位置 / 投票**都能用
（投票只在群聊里。**没有「收藏」** —— 收藏的作用对象是已有的一条消息，
长按消息就能收藏，见下）。

几个不显然的点：

- **视频有两种来源，都要认。** `kind === 'video'` 是走「视频」入口发的；而在没有视频入口之前，
  视频只能走「文件」发出去，库里存的是 `kind='file'`。前端 `isVideoMessage()` 按扩展名补判一次 ——
  只认前者的话，用户早先发的那些视频点开仍然是死的，他会认为这次没改好。
  `check-media.mjs` 的 C 段专门钉这条兼容路径。
- **`messages.kind` 加 `video` 是一次整表重建。** SQLite 没有 `ALTER CONSTRAINT`，
  改 CHECK 只能重建表（`db.js` 的 `rebuildMessagesForVideo()`：`foreign_keys=OFF` 必须在 `BEGIN` **之前**，
  建新表 → 拷数据 → 删旧表 → 改名 → 重建索引，全程一个事务，结束跑 `foreign_key_check`）。
  幂等，老库直接启动即可 —— **不用跑 `npm run reset`**（那会连会话和消息一起清掉）。
- **视频气泡里不要放 `controls`。** 气泡本身就是个 `<button>`，
  而 `video[controls]` 属于 interactive content，套在按钮里是非法嵌套（React 会告警）。
  气泡只用来显示首帧 + 播放角标，播放交给查看器。
- **查看器里的视频也不用原生 `controls`**（2026-10 起换成自建播放器）：原生控件会带出
  「画中画 / 下载」这些**没接**的按钮 —— 点了没反应，在用户看来就是坏功能；
  而且它不管容器比例、各浏览器长得不一样，一个 App 里会出现两套视觉语言。
- ★ **但「不用原生 `controls`」≠「看起来不像默认播放器」。** 这一点踩过一次：控件全是自建的、
  `video[controls]` 也是 false，可第一版查看器把容器写成 `height:100% + max-height:none` —— 容器撑满整个舞台，
  画面 `contain` 居中后上下各留一大片纯黑，控制条被 `bottom:0` 推到屏幕最下沿（实测离画面 59px），
  顶上还压着一行原始文件名。用户第一眼就认定「你用的还是默认播放器」。
  判定「像不像原生」的其实是**布局**，三条可量化的形态：
  **容器正好是画面的形状**、**控制条贴在画面下沿的玻璃胶囊上**、**画面上一个字都不叠**。
  `check-video.mjs` 用 `window.__mvBox()` 钉住了这几条（比例差 ≤ 0.02、控制条间距 ≤ 16px、
  容器高 < 舞台高 × 0.8、**左右余量差 ≤ 2px**）—— 只断言「没有 `controls` / 有自己的 `.vp-bar`」
  是抓不到这个 bug 的。外层 `.mv-vp` 只负责居中，**不要再去改写 `.vp-root` 的尺寸**
  （旧文档里那句「两个上限一起解」是错的，照做就是上面那个 bug）。
- ★★ **查看器/全屏那套布局挂在 `is-full` 上，而 `is-full` 由 `mode === 'full' || full` 一起驱动。**
  这里也踩过一次：类名原来只由 `full`（= 浏览器 Fullscreen API 生效中）驱动，
  `mode="full"` 的查看器**永远拿不到它** → 整段 `.vp-root.is-full` CSS 是死代码。
  横屏看着正常是巧合（基础规则的 `width:100%` 恰好铺满查看器宽度）；竖屏就露馅了 ——
  套的是**列表卡片**的规则（`max-width: 380×0.6 = 228px` + `margin-right: auto`），
  228×380 的卡贴在左边缘、没居中（用户看截图问「这是竖屏对吗」才发现）。
  **写完一段 CSS 要确认它真的被用上**：类名由某个状态驱动时，先确认那个状态在目标场景下为真。
- **查看器用未夹取的真实比例**：比例夹取（0.6~1.91）是为了别让极端比例撑爆**信息流卡片**，
  查看器已经有 `max-height:100%` 兜底。继续夹只是白送黑边（真实 0.563 被夹成 0.6 → 左右各 11px 黑条）。
  做法：额外写一个 `--ar-true`（`rawAspectOf()`），`.vp-root.is-full { aspect-ratio: var(--ar-true, var(--ar)) }`。
- ⚠️ **浏览器全屏态的尺寸/位置改不动**：UA 的 `:fullscreen` 规则带 `!important`
  （`position:fixed / inset:0 / width:height:100% / margin:0 / transform:none`），
  作者写 `top/left:50% + translate(-50%,-50%)` 完全不生效（实测元素仍在 `(0,0)`、`100vw×100vh`）。
  所以别写那不是死代码就是幻觉 —— 全屏就是「铺满整屏 + 画面 `contain` 居中 + 控制条在屏幕底部」，
  这正是全屏播放器的通行形态。只清掉卡片感：`.vp-root.is-full:fullscreen { border-radius:0; box-shadow:none }`。
- **控制条 5 秒没用会自动收起**（`BAR_AUTO_HIDE`），暂停 / 播完 / 指针移入 / 点画面立刻回来。
  收起后是 `pointer-events: none`，靠 `onPointerMove` 叫回来 —— 所以自检的点击要**先 `mouseMoved` 再按下**。
- **查看器的背景用 `backdrop-filter`**，和项目里其它浮层一个语言。
- 服务端视频扩展名白名单（`upload.js` 的 `VIDEO_EXT`）和前端 `isVideoMessage()` 用的是**同一份清单**，
  必须同步：前端认而服务端不认的话，选完视频会在发送那步被 400 挡掉，报的却是「文件地址不合法」。

## 扫一扫 / 我的二维码

两个入口、三条路径、四种结果，**全部是真实动作**：

| 入口 | 位置 | 内容 |
| --- | --- | --- |
| 我的二维码 | 我页 ID 卡右上（昵称行最右） | 展示自己的码（`chatly://user/<ID>`）+ 保存卡片图 + 复制 ID |
| 扫一扫 | 聊天页顶栏（搜索键右侧） | 摄像头扫码 / 从相册选图 / 手动输 ID |

> ⚠️ 我页那个位置原本被「更换主页背景」占着（封面右下角 = id 卡右上角，见下），所以顺手把
> 「换背景」挪到了封面的上沿右角 —— 两个 32px 圆按钮各占一角，互不遮挡。

识别到之后：

| 码里是什么 | 界面做什么 |
| --- | --- |
| `chatly://user/<ID>` | 资料卡（头像 / 昵称 / 签名 / 标签 / 在线）→ **加好友**（写 `follows` 表）+ **发消息**（建/开私聊） |
| 自己的码 | 标「这是你自己的码」，**不给**加好友按钮（点了必然报错） |
| `chatly://group/<id>` · `chatly://moment/<id>` | 认得出类型，写明「会在后续版本加入」，**没有任何加入按钮** |
| `http(s)://…` · 纯文本 | 原样展示 + 复制（网址**不自动打开**）；像用户 ID 时多给一个「按这个 ID 查一下」 |

后端为此加了 `GET /api/v1/users/by-username/:username` —— 界面上的「ID: xxxx」是 username，
扫到 / 手输只能拿到它，得先换成数字 id 才能复用资料与关注那套逻辑。
它和 `/:id` **共用同一个响应体构造函数**（`viewerPayload`），免得加字段只补一边。

### 为什么编解码都是自己写的

桌面 Chrome **没有 `BarcodeDetector`**（Shape Detection API 没开），项目又硬约束零运行时依赖
（不引 `qrcode` / `jsqr` / `zxing`）。所以 `src/lib/qr.js` 从 GF(256) 到仿射采样全部自己实现：

- **编码**：byte 模式，纠错 L / M，版本 1~10（17~271 字节）。八种掩码全试一遍，
  按标准惩罚分选最优。给「我的二维码」用。
- **解码**：灰度 → Otsu 二值化 → 1:1:3:1:1 定位图案检测 → 仿射采样（**容旋转 / 倾斜 / 缩放**）
  → 反掩码 → 去交织 → RS 纠错 → 解析负载。给「扫一扫」用。
- 不支持：透视畸变（要第 4 个角点做单应变换）、一图多码、非 byte 模式。

### 不显然的几个点

- ★★ **编解码必须共用同一份 Z 字填充顺序**（`dataPositions()`）。编码器写一遍、解码器读一遍的话，
  两边差一个模块就是「码画出来很好看、扫出来是乱码」，而且**自己编自己解照样能过**（错得一样）。
- ★★ **`functionMask` 的三个角块不是三个 9×9** —— 左上 9×9（含格式信息第 1 份），
  右上 9×8、左下 8×9，各差一行/一列。多标一列/一行会把本该放数据的模块当成功能模块，
  Z 字顺序随之整体错位。这个错**只看代码看不出来**，是和参考实现对拍 `reservedBit` 才定位到的。
- ★★ **RS 生成多项式那两行极易写反**（`next[j] ^= g[j]` 与 `next[j+1] ^= α^i·g[j]`）。
  写反之后 g 的前几项全错，但**编解码仍然自洽**（共用同一份 g），自己的码自己扫得出来 ——
  只有和标准实现逐模块对拍、或者拿真扫码器扫才会暴露。
- ★ **这套东西必须用第三方实现对拍，自己验自己等于没验。** `scripts/lib/qr-verify.mjs`
  拿 npm 上的 `qrcode` + `jsqr` 当裁判，69 项：版本一致、**掩码 0~7 逐模块一致**、
  自动选掩码一致、`jsqr` 能解我编的码（含 0/90/180/270 旋转、缩放、噪声）、
  自解码器能解同样的图。依赖装在 `.tmp/qrverify/`，不进项目依赖。
  跑：`node scripts/lib/qr-verify.mjs`
  ⚠️ 顺带一个坑：`qrcode` 库的 `{ mode: 'byte' }` 选项**不生效**（会自作主张选 Alphanumeric），
  要强制 byte 只能 `new ByteData(text)` 当段传进去 —— 不加这一步，「HELLO」这类纯大写样例
  会一直对不上，看起来像自己的编码器有 bug。
- ★ **码中心不放头像。** 自写解码器每块最多纠 3 个错误码字，中心挖一块出来很容易超掉纠错能力，
  症状是「自己截图再扫自己的码，扫不出来」。头像放在码外面的卡片里。
- ★ **缩放取整数像素/模块**，并把 canvas 的 CSS 尺寸钉成它的像素尺寸。
  让浏览器按非整数倍缩，模块边缘会被重采样成灰边，真机扫起来更容易失败。
  用长一点的 username（版本 3）会换一个整数缩放，所以缩放是按版本算的，不是写死的。
- ⚠️ **「我的二维码」和「更换主页背景」抢同一格，必须错开。** `.me-idcard` 用 `margin-top:-44px`
  上浮压住封面底部 44px，所以「封面右下角」和「id 卡右上角」在几何上是**同一个位置**，
  而 `.me-idcard` 还带 `z-index:2` 压在封面之上。二维码入口一放进昵称行末尾，
  「换背景」按钮就被**整个盖住、点不到**（它照样在 DOM 里、`disabled` 仍是 false，
  所以只断言「按钮存在」必假绿）。现在「换背景」挪到封面的**上沿右角**
  （`top: calc(var(--safe-top) + 6px)`），两个 32px 圆按钮各占一角。
  `check-qr.mjs` 量的是**交叠面积 + 两个按钮各自中心 `elementFromPoint` 的归属** ——
  反例：把样式改回 `bottom: 14px`，会报 **840px² 交叠**、且「换背景」中心点不到自己。
- **扫一扫是整屏**深色覆盖层（浅底会把摄像头画面衬得发白），且不给摄像头时**必须写明具体原因**
  （权限被拒 / 没设备 / 被占用 / 非安全上下文），并且相册与手动输入照常可用 ——
  显示一个永远不会动的「正在扫码」是最糟的降级。
- **`getUserMedia` 起流后每 260ms 抽一帧**，缩到最长边 480 再解（解码耗时几乎只跟像素数走，
  1280×720 全尺寸会卡）。识别到立刻停流并锁住（同一帧会连着命中好几次）。
- **「重试」不能用 `setResult(null)` 触发重开**：结果本来就是 null 时 setState 值没变，
  effect 依赖数组没变化 → 根本不重跑，按钮点了像没反应。用一个自增计数器。
- **`nav.openChat()` 之前先关掉扫一扫**：`openChat` 只是把房间层叠上来，
  扫一扫不退场的话两个整屏层会叠在一起。
- 群码这一档**刻意只做到「识别出类型」**。后端还没有群邀请 / 入群码校验，做成按钮就是个
  点了没反应的假东西（见「不做假功能」）。

## 表情面板

输入框右侧的表情按钮打开面板，分「表情」与「大表情」两档。

|     | 表情                                                    | 大表情               |
| --- | ----------------------------------------------------- | ----------------- |
| 点一下 | 在输入框**光标处**插入一个真实 Unicode 字符                          | 直接发一条贴纸式大图消息      |
| 候选  | 9 个分组（笑脸 / 手势 / 动物 / 自然 / 食物 / 旅行 / 活动 / 物品 / 符号）+ 搜索 | 47 个精选（单独发也成立的那些） |
| 渲染  | 跟随系统字体，与文字一起排，可复制                                     | 96×96，无气泡无边框      |

- **最近使用**存在浏览器 `localStorage`（纯本地偏好，不进后端），用过的排在最前，最多记 18 个。
- 搜索按**中文名**匹配（名字取自 Unicode CLDR 中文注释），也可以直接粘码点。
- 打开方式：点表情按钮开合、点输入框收起、点消息区收起、`Esc` 收起；正在打字时表情按钮依然在（不会变成只剩发送）。
  > **点输入框收起面板**这条看着简单，但有个必踩的坑：判据**不能用 `focus` 事件**去做。
  > 挑完一个表情后 `insert()` 会 `el.focus()` 把光标放回输入框，
  > 而真机点表情按钮会让 textarea 先失焦 —— 那次程序性 focus 就会真的触发 focus 事件，
  > 于是「挑一个表情面板就被自己关掉」，根本没法连续挑。
  > 判据只能认「面板开着 + 用户自己点了输入框」，即 `pointerdown` / `click`。
  > `check-emoji.mjs` 的 F 段把正反两面都钉住了：正向「点输入框收起」，
  > 反向「★ 挑表情后面板仍然打开」——后者还专门用真实鼠标事件打开面板，
  > 好让 textarea 真的处于失焦状态，否则这条反例没有鉴别力（已造反例验证它会失败）。

**素材与授权**

386 个素材全部是 [Microsoft Fluent Emoji](https://github.com/microsoft/fluentui-emoji) 的 **Color** 风格彩色 SVG，  
授权 **MIT**（免署名，许可证原文落在 `public/emoji/LICENSE.txt`）。刻意**不使用 CDN** ——  
本项目要求离线可跑、无 404，所以素材必须落在本地。每个表情是**独立文件**，面板只加载当前可见的那一屏，  
7.6MB 是磁盘体积而不是首屏体积。

重新抓取 / 更换风格：

```bash
node scripts/fetch-emoji.mjs            # 复用缓存，只补缺失的素材
node scripts/fetch-emoji.mjs --reindex  # 重新拉全量 metadata 索引（上游目录结构变了才需要）
```

脚本里有三件事值得知道：

1. **码点只能从上游每个 `metadata.json` 读**，猜不出来 —— 所以要建 1595 条索引。
2. **上游有两种目录布局**：普通表情在 `assets/<名>/Color/<名>_color.svg`；  
   可换肤色的（如「合十」「竖起大拇指」）**没有 `Color` 直属目录**，只有  
   `assets/<名>/<肤色>/Color/`，我们取 `Default`（标准黄）。而且文件名里保留 `-` 和 `!`，  
   所以脚本是拿 27127 条文件树**正则匹配真实路径**，不拼字符串。
3. **不能按码点顺序取前 N 个** —— "Animals & Nature" 里码点最小的是一串冷门啮齿动物，  
   🐶🐱🐼 都排在后面，按顺序截断会得到一份「全是老鼠」的动物面板。  
   所以分组是**按常用度手写的优先清单**，脚本会把对不上的码点报出来。

**大表情为什么要复用 `kind='image'`**：`messages.kind` 上有 `CHECK (kind IN ('text','image','file'))`，  
SQLite 改 CHECK 要重建表。贴纸用的是本地 `/emoji/...` 地址，客户端按 `fileUrl` 前缀判断该画成贴纸还是图片 ——  
和头像的 `preset:<n>` 一个思路，**零数据库迁移**。

### 动画大表情

47 个大表情里，上游做了动画版的有 **30 个**，走 `public/emoji-anim/<码点>.gif`；  
其余 17 个（多是手势类：👍👏🙏💪🤝）上游没做动画，前端自动**回退静态 SVG**，形态仍然是贴纸。

素材来自 **另一个仓库** [microsoft/fluentui-emoji-animated](https://github.com/microsoft/fluentui-emoji-animated)（447 个，同为 **MIT**）。  
主仓 `fluentui-emoji` 里一个动画文件都没有 —— 只有 Color / Flat / High Contrast 的 SVG 和 3D 的 PNG。

上游给的是 **APNG**（256×256、40+ 帧、**单个 2.85MB**），全量 447 个约 1.3GB，必须本地转码：

```bash
node scripts/fetch-emoji-anim.mjs            # 缺什么下什么（原始 APNG 缓存在 .tmp）
node scripts/fetch-emoji-anim.mjs --force    # 忽略已有产物，全部重转
```

转码参数实测择优（同一张「笑得满地打滚」，固定 fps=10、取第 5 帧）：

- **噪点** = 像素与其 3×3 邻域均值的偏差（GIF 只有 1-bit alpha，边缘的锯齿/脏点都体现在这里）
- **锯齿** = 降到显示尺寸后的边界周长 / √面积（这个量几乎不随尺寸变，说明它不是毛刺的主因）

| 产物（尺寸 / 色数 / 抖动） | 体积 | 噪点 | 锯齿 | 判定 |
| ------------------------- | ---- | ---- | ---- | ---- |
| 112 / 96 色 / bayer3（第一版） | 96KB | 5.78 | 4.50 | 毛刺明显 |
| 112 / 128 色 / bayer1 | 127KB | 7.71 | 4.50 | 抖动反而更脏 |
| 112 / 256 色 / 无抖动 | 110KB | 5.20 | 4.50 | 尺寸太小 |
| 144 / 256 色 / 无抖动 | 153KB | 4.07 | 4.50 | 可用 |
| 160 / 128 色 / bayer1 | 220KB | 6.40 | 4.49 | 超体积上限 |
| **160 / 256 色 / 无抖动** | **~175KB** | **3.71** | 4.49 | **采用** |

结论有两条，都和直觉相反：

1. **毛刺的主因是抖动噪点，不是分辨率。** 尺寸从 112 加到 160，锯齿几乎不动（4.50 → 4.49）；
   而把抖动关掉、色数拉满 256，噪点 5.78 → 3.71。加大抖动（bayer1/bayer3）只会把噪点推到 7.7。
2. **帧数是体积主因**（40+ 帧），抽帧比降色有效得多。超过 190KB 会自动降档重编。

最终 30 个共 4.47MB、平均 153KB。**素材带缓存头**（见下），首次看过之后走本地副本。

> **素材本地缓存**
>
> `vite.config.js` 里有个 `emojiCacheHeaders()` 插件，给 `/emoji/` 和 `/emoji-anim/` 两个前缀加
> `Cache-Control`：开发期 `public, max-age=3600`，构建产物 `public, max-age=31536000, immutable`。
> 素材是内容寻址的（文件名 = 码点，改素材就换文件名），所以可以放心长缓存。
> `check-emoji.mjs` 有对应断言，实际请求一次校验响应头真的带 `max-age`。
>
> 两个前缀都要判 —— `'/emoji-anim/1f602.gif'.startsWith('/emoji/')` 是 **false**（少一个斜杠），
> 只写一个中间件的话动画素材会静默地不带缓存头。

> **为什么是 GIF 而不是 WebP**
>
> 第一版转的是 WebP 动画，桌面浏览器上出现「一个表情叠着另一个、还错位」。  
> 根因不在像素，在**帧语义**：ffmpeg 的 libwebp 写出的帧是
> **全画布 + `blend` + `dispose=none`**（每帧混合到上一帧、且不清除上一帧），
> 而 Fluent 表情的背景是**透明**的 —— 透明处透出上一帧，动作幅度大的（🤣💩🚀）
> 就是一眼可见的两个表情叠着，动作小的（😂）表现为拖影。
>
> GIF 没有这个问题：ffmpeg 的 gif 封装写 **`disposal=2`（显示后恢复背景）**，每帧结束把画布擦干净。  
> 转码脚本会**逐个校验**每帧的处置方式，不是 2 就打补丁；`scripts/check-emoji.mjs` 用同一份判据
> （`scripts/lib/gif.mjs`）再验一遍 —— 判据只有一份，两边才不会各说各话。
>
> 交叉验证过这个判据确实有效：把某个表情的 disposal 改成「不处置」后，
> 规范播放到最后一帧的不透明面积 `0.621 → 0.678`、包围盒 `100×102 → 106×107`
> （超出任何单帧），残影立刻现形。
>
> ⚠️ **补丁代码必须造反例跑一遍。** 补丁函数第一版把 `gceOff` 指到了 GCE 的「块长度」字节
> （`packed` 其实在 `off+1`），打上去会改坏块长度、文件直接解不开。这个 bug 一直没暴露：
> ffmpeg 本来就写 `disposal=2`，补丁从不触发 —— 也就是说这条路径**从没被执行过**。

这条路还有三个坑，都写在脚本头里：

1. **Git LFS**：`raw.githubusercontent.com` 对这批图只返回 **132 字节的指针文本**，  
   真身必须走 `media.githubusercontent.com/media/{owner}/{repo}/{branch}/{path}`。  
   脚本会挡住小于 1KB 的响应，避免写出一堆坏图。
2. **文件名不能自己拼**：`smiling_face_with_heart-eyes_animated.png` 保留连字符，  
   按「非字母数字都换下划线」拼会拼出不存在的文件（第一版就漏了 😍）。路径只能从文件树取。
3. **前缀要认两个**：`isEmojiSticker()` 必须同时认 `/emoji/` 和 `/emoji-anim/` ——  
   `'/emoji-anim/1f602.gif'.startsWith('/emoji/')` 是 **false**，只判一个会让动画贴纸退化成带气泡的普通图片。

## 设计规范

⚠️ **脚本会自己挑空闲调试端口**（`scripts/lib/cdp.mjs` 的 `freePort()`，可用 `CDP_PORT` 覆盖）。
别改回写死端口：本机多项目并行时固定端口会被别人的浏览器占掉，
`waitTarget()` 拿到**别人的页面**当成自己的，然后报出「应用可能没挂载」——
结论指向完全错误的方向（去查前端挂载，而真凶是端口冲突）。
同时 `waitTarget()` 只认 `url` 以本应用前缀开头的 target，端口被占时会直接说
「端口被别的浏览器占用了（页面是 …）」而不是含糊地超时。

⚠️ **别把多个 CDP 脚本塞进一个 `for` 串行跑**：上一个 Chrome 未必已退出，
下一个会连到旧浏览器，报出「语法错误」「waitFor 超时」这种看起来像代码坏了的假象。单独跑。

⚠️ **浏览器连不上本机端口时，先看代理环境变量**。这台机器上设了 `http_proxy` / `HTTP_PROXY`，
Chromium 被代理接管时会连 `127.0.0.1` 都走代理，页面直接变成 `chrome-error://chromewebdata/`，
自检报「应用没挂载」—— 而 `curl` 打同一个端口是 200。这个假象极有迷惑性（会让人去查前端挂载）。
`scripts/lib/cdp.mjs` 的 `launchChrome()` 已固定加 `--no-proxy-server`，别删。

### 自检**不能假设演示库是干净的**

发现页上就有「关注 / 加入群」按钮，用户会在预览里随手点。自检如果写死
「陈宇当前没被关注」「`/discover/groups` 至少有一个群」，用户点两下之后就会：
崩在 `groups[0]` 是 `undefined` 上，或者更糟 —— **报出一个方向完全错误的结论**
（比如动态自检报「不该看到的人看到了」，真因是用户把陈宇关注回去了，可见性代码一点问题没有）。

所以每个脚本都要**自己造前提**，并在收尾还原：

- 关注测试对象先归一到「未关注」，记下原状，`finally` 里还原（`check-discover.mjs`）。
- 加入群测试**现建一个公开群**（换个账号当群主，标题带 `自检·` 前缀交给 `purgeDebris`）。
- 打招呼对象从库里**现查**「本来就和他有私聊」的人 —— 写死的话，用户「删除会话」（=退出自己）之后
  这一步就会失败在一个跟发现页毫无关系的原因上。
- 可见范围测试把关系图（`互关 / 单向关注`）**显式摆正**再还原（`check-moment.mjs` 的 `normalizeGraph()`）。

判断依据很简单：**这个前提，用户能在界面上改掉吗？** 能，就必须自己造。

### 自检脚本会自己收拾现场

CDP 脚本会临时建会话 / 发探针消息，跑完必须真删掉，否则演示库会被越跑越脏。  
⚠️ **`DELETE /conversations/:id` 删不掉会话** —— 它的产品语义是「退出成员关系」，  
会话行、消息、其他成员的成员记录都会留着。自检脚本一度以为删掉了，结果攒下 57 个会话  
（其中 13 个同名「回执演示·部分」）。所以清理统一走 `scripts/lib/debris.mjs`，  
按标题前缀（`自检·` / `回执演示·` / `联调群` / `收件人小组`）加「零成员孤儿」直接删库。


**消息清理按「基线」而不是按「记住的 id」。** 开跑前记下 `maxMessageId()`，收尾 `purgeMessagesAfter(基线)`。  
逐个收集 id 的做法一定会漏 —— **撤回测试最容易漏**：撤回不是删除，消息行还在（`revoked_at` 有值），  
界面上就是一条「消息已撤回」。演示会话里攒下这种空行，看的人只会以为产品出了 bug。  
`server/test/e2e.mjs` 就靠这招把「每轮留下 1～3 条」降到了 0。

`check-profile.mjs` 的收尾还要更小心一层：换头像会顺手删掉旧文件，  
所以「还原」必须**先把原文件字节写回磁盘、再写字段**，顺序反了会被悬空引用校验挡下。  
这条坑 `e2e.mjs` 也踩过 —— 只 PATCH 字段于是整个请求 400，演示库里留下一个「陈墨·测试」当好几天。

上传文件由 `purgeOrphanUploads()` 统一回收：扫 `users.avatar` + `messages.file_url` 两处引用，  
没人指的**移到** `.tmp/orphan-uploads/`（不删，误判了还能捞回来）。  
⚠️ 必须在清完消息之后再调 —— 反过来的话刚发的图还被消息指着，扫不到。

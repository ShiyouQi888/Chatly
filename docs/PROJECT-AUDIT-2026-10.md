# Chatly 项目功能、逻辑与缺陷审计

- **审计日期：** 2026-10-22
- **项目版本：** 当前工作区代码（包含尚未提交的变更）
- **审计方式：** 静态代码审阅、前后端调用链对照、配置与部署文件审阅、已有专项检查脚本清单审阅
- **运行情况：** 本次未启动服务、未执行自动化测试、未进行真实浏览器或线上环境验证，也未执行依赖漏洞扫描。

## 1. 总结

Chatly 已具备较广的即时通讯产品功能：邮箱验证注册、私聊与群聊、好友申请、动态、状态、文件、群公告、投票、已读与阅后即焚、独立运营后台，以及 SQLite/PostgreSQL 双数据库和 Docker 部署配置。手机号注册入口目前关闭，服务端实现仍保留。

**当前判断：适合持续开发和受控试运行，正式公开上线前仍需完成运行环境验证。** 本轮已修复本报告列出的好友申请渠道绕过、WebSocket 长期 JWT 暴露、非好友私聊会话创建、私聊并发重复、负数分页、动态媒体孤儿文件和多实例限流共享问题，并更正账号安全功能清单。修复来自静态代码修改，尚未执行自动化或运行环境验证。

本报告列的是从代码路径核实的缺陷和上线风险，不代表已经复现运行时行为。严重度按现有实现和影响范围估计。

## 3. 已确认问题

### P1-1：好友申请可通过省略 `source` 绕过对方的添加权限（已修复）

好友申请路由现在要求 `source` 必须属于 `qr`、`phone`、`search`，缺失或未知时返回 400；有效来源会在服务端读取目标用户隐私设置并调用 `canAddBy()`。发现推荐入口明确按搜索渠道提交。此前版本省略来源时会跳过检查。

- **修复位置：** `server/src/routes/users.js`、`server/src/privacy.js`、`src/store/DiscoverStore.jsx`。
- **影响：** 隐私设置未能成为可靠的服务端访问控制；可能收到不希望收到的好友申请。
- **剩余边界：** 目前客户端声明来源，服务端验证来源白名单并执行对应隐私开关；服务端无法从请求本身证明 UI 来源。任何来源都至少受其对应开关约束。

### P1-2：WebSocket JWT 放在 URL 查询参数，存在访问日志泄露风险（已修复）

WebSocket 现从 `?ticket=...` 接收一次性随机票据：前端先经受保护的 REST 接口申请，票据只存 SHA-256 摘要、绑定用户和登录会话、60 秒过期，并通过原子 `DELETE ... RETURNING` 消费。Nginx 的 `/ws` 访问日志也已关闭。代理链路仍可能记录短时票据，但票据单次消费后不可重放；部署仍应使用 HTTPS/WSS。

- **修复位置：** `server/src/ws.js`、`server/src/routes/auth.js`、`src/api/client.js`、`src/hooks/useChatSocket.js`、`docker/nginx.conf`。
- **剩余边界：** 外层代理或托管负载均衡是否记录 `/ws` 查询参数取决于部署配置；即使记录，票据也只能成功使用一次且有效期为 60 秒。

### P2-1：任意登录用户可以为任意用户创建私聊会话，且不要求互为好友（已修复）

私聊会话创建现在先确认目标用户存在，再通过 `privatePairGate()` 校验双方互为好友且没有删除关系；否则返回相应 403 错误。

- **修复位置：** `server/src/routes/conversations.js`、`server/src/friends.js`。

### P2-2：私聊“查找后创建”没有并发去重，竞争请求可能生成重复会话（已修复）

`ensurePrivate()` 现在将用户 ID 排序后在 `private_conversation_pairs` 表中建立唯一映射，并在事务内查找、创建和映射；数据库唯一键解决跨进程竞争，本进程队列串行化并发的私聊创建。旧会话按 ID 最早的一条建立映射，新调用统一复用该会话。

- **修复位置：** `server/src/chat.js`（惰性创建规范化用户对索引表并映射历史会话）。
- **剩余边界：** 历史数据库中已经存在的多条重复私聊不会被自动合并或删除；新请求会稳定复用最早映射的一条。

### P2-3：聊天历史接口接受负数 `limit`，SQLite 下可能退化成无上限查询（已修复）

会话消息路由现在要求 `limit` 是正安全整数，超出上限时限制到 100；`beforeId` 也必须是正安全整数。无效值返回 400，避免 SQLite 和 PostgreSQL 对负数分页的不同处理。

- **修复位置：** `server/src/routes/conversations.js`。

### P2-4：动态媒体在编辑、删除或放弃发布时不回收（已修复）

编辑替换或删除动态媒体后，服务端会确认文件没有被其他数据引用，再立即删除文件。生产后端另每 24 小时扫描一次超过 24 小时且无引用的公开上传文件，覆盖放弃发布或上传后未提交的媒体。引用表包含反馈截图、收藏快照、用户头像/封面、群头像、动态媒体和消息文件。

- **修复位置：** `server/src/moment.js`、`server/src/upload-cleanup.js`、`server/src/index.js`。
- **剩余边界：** 媒体上传地址在被引用或超过 24 小时清理前仍是公开静态地址；正式公开媒体访问策略仍需产品侧决策。

### P2-5：限流器只存在于单个 Node 进程（已修复）

认证限流现在存于共享数据库的 `auth_rate_limits` 表，以原子 upsert 更新窗口计数，并周期清除过期行。使用共享 PostgreSQL 的多个后端副本和服务重启会保留同一份计数；SQLite 单机部署也使用相同逻辑。

- **修复位置：** `server/src/auth-limit.js`。
- **剩余边界：** 多实例部署必须共享同一个数据库；不同数据库实例仍各自计数。短信/邮件供应商侧的成本预算与告警仍需运营配置。

### P3-1：可见功能清单与“已接入/未接入”边界不一致（部分修复）

README 账号安全表格已更正：明确邮箱注册和验证已接入、手机号注册入口暂时关闭但服务端实现保留，且手机号/邮箱字段可在资料页查看或维护。当前发现页活动报名和热门话题均有服务端接口，不再将其作为未接入问题；其余 README 功能表仍应随产品变更定期核对。

- **修复位置：** `README.md` 账号与安全功能表格。
- **后续维护：** 继续按“端到端可用 / 有限制 / 未接入”标注配置前置条件。

## 5. 已有防护与实现优点

- 普通用户 JWT 会同时检查签名、账号状态和数据库设备会话；管理员会话使用独立 token 和表，不复用普通用户账号。
- 多数 API 按会话成员、动态可见性、作者身份或运营角色在服务端授权；群发言门控包含普通消息、转发和投票入口。
- 私聊附件通过成员关系授权；阅后即焚消息在历史、搜索、最近文件和后台读取路径中设置了到期过滤，且执行清理。
- 动态视频在类型检查之外读取文件头魔数；消息文件地址有自有资源前缀和路径形状检查。
- 数据库使用参数化查询；已有测试脚本覆盖多项过去出现过的业务回归点；Docker 示例将数据库、Redis 和后端限制在内部网络。

以上是对代码结构的确认，不代表本次已运行验证这些防护在 SQLite、PostgreSQL、Redis 和反向代理组合下都正确。

## 6. 上线前观察项

1. **正式环境配置：** 生产 `JWT_SECRET`、OTP 密钥、数据库密码、管理员口令和邮件/短信供应商密钥必须使用独立强随机值；不要把 `.env`、生产数据或密钥打进部署包。`VITE_TMAP_KEY` 会进入浏览器构建产物，应配置来源限制。
2. **传输与代理：** 只通过 HTTPS/WSS 对公网服务；限制后端、数据库和 Redis 的网络访问；确认 `TRUST_PROXY_HOPS` 与真实代理拓扑相符，避免伪造客户端 IP 绕过按 IP 的限制。
3. **消息隐私：** `MESSAGE_ENCRYPTION_KEY` 要单独备份并制定轮换/恢复方案。当前 AES-GCM 加密由服务端解密，因此有服务器密钥权限的管理员/进程仍可读取正文。
4. **备份和日志：** 数据库、`uploads`、`private-uploads` 和解密密钥需要协同备份并定期隔离恢复演练；部署平台应采集日志、监控磁盘、数据库、Redis 降级、重启与消息错误率。当前仓库未提供自动化备份恢复或告警闭环。
5. **内容治理：** 管理后台具备用户停用、内容处理和私聊读取能力，但生产运营仍需制定审核标准、申诉流程、私聊查阅授权、数据留存和管理员审计复核流程。
6. **规模边界：** 消息搜索受候选条数上限约束；`listConversations()` 目前按每个会话额外查询最后消息、未读数和成员，属于随会话数量增长的多次查询。小规模可接受，规模增长后应做批量查询和关键索引/慢查询监控。
